## Implementation and boundaries

- Server-authenticated ephemeral ML-KEM-768 exchange using a provisioned
  ML-DSA-65 public-key pin. Clients remain anonymous.
- Canonical transcript binding, separately derived confirmation/traffic keys,
  bidirectional confirmation, ordered bounded AES-GCM records and owned key disposal.
- An in-process round trip and 17 explicit rejection checks, with separate tests
  for framing, trust snapshots, KEM-key substitution, nonce/counter limits,
  cancellation and strict CLI policy.
- Additive --session, --strict and repeatable --require switches. Unsupported or
  missing required algorithms fail with a nonzero exit code.
- Dedicated security CI with a digest-pinned native-provider container and
  anonymous report validation. Existing runtime CI remains in place.

These are internal types in the existing net10.0 lab. No project, runtime
dependency or public SDK declaration is added. Library targets remain net9.0,
assembly binding stays 1.0.0.0 and package validation keeps the reviewed 1.0.0
baseline. Existing v1.7 quantum experiments and discovery-mode reports are retained.

## Security assumptions

The NIST section 5.2.3 example supplies the high-level exchange pattern. Pin-based
trust provisioning, framing, confirmation and records are explicit lab adaptations,
not a reviewed production or interoperable protocol. There is no socket service,
certificate chain, mutual client authentication, key-update protocol, persistent
key store, side-channel assessment or full security certification. Endpoint and
provider compromise remain outside this experiment. Tests are correctness evidence
under the documented model, not a protocol-security proof.
